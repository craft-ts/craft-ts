# Plan — i18n typé, robuste et intégré à la création d’applications Craft TS

## Objectif

Ajouter un mécanisme de traduction indépendant d’Effect TS qui garantit :

- une union fermée de clés de traduction ;
- une parité exacte entre les locales ;
- des paramètres typés pour les messages ;
- des tokens sémantiques pour `money`, `date`, `number`, `percent`, etc. ;
- la gestion correcte des pluriels selon chaque locale ;
- des tests sur les pages réelles de l’application ;
- une vérification de la fonte, de la taille, de l’interligne et du layout ;
- une installation et une configuration automatiques par `craft create`.

## Décisions structurantes

### Le package de base reste indépendant d’Effect TS

Le package principal proposé est :

```text
@craft-ts/i18n
```

Il ne doit pas dépendre de :

```text
effect
@craft-ts/effect
```

Il expose uniquement les concepts génériques : catalogue, message, token,
formatter, locale, loader, validation et test matrix.

Effect Schema pourra être utilisé localement dans une application plain, mais
le package de base ne l’impose jamais.

Un package d’intégration séparé est prévu pour les applications qui choisissent
Effect TS :

```text
@craft-ts/i18n-effect
```

Ce package sera installé et configuré automatiquement uniquement en mode
`effect` de `craft create`.

### Le package fournit des extensions, pas un catalogue métier fermé

La bibliothèque fournit des primitives génériques permettant à l’application
de créer ses propres utilitaires :

```text
money()
date()
number()
orderStatus()
customerName()
subscriptionPlan()
```

Les utilitaires spécifiques restent dans l’application et ne sont pas ajoutés
à `@craft-ts/i18n`.

### Les traductions et le formatage sont séparés

Un message contient du texte et des tokens sémantiques. Le token porte le nom,
le type attendu et le formatter à utiliser. Le formatter dépend de la locale
active et des règles du projet.

```text
valeur métier → token typé → formatter localisé → texte final
```

## Architecture proposée

### Package principal

Créer une nouvelle bibliothèque :

```text
libs/i18n/
```

Avec une surface publique minimale couvrant :

- `defineCatalog` ;
- `defineLocale` et `defineLocaleLike` ;
- `msg` ;
- `plural` et éventuellement `select` ;
- `defineToken` et `defineTokenFactory` ;
- types `TranslationKey`, `TranslationParams`, `LocaleId` ;
- `createI18nRuntime` ;
- `createI18nLoader` ;
- validation de catalogue ;
- exports de test.

Le runtime doit rester indépendant de Craft TS. Une intégration Craft pourra
être ajoutée comme sous-surface sans imposer Angular, Effect ou un renderer.

### Tokens typés

Le package doit permettre de créer un token à partir d’un type générique ou
d’un adapter de schéma fourni par l’application :

```text
defineToken<Name, Value>({
  name,
  kind,
  validate?,
  format,
})
```

La bibliothèque ne connaît pas `Money`, `OrderStatus` ou `Customer`. Elle
connaît uniquement `Value`.

Une application utilisant Effect Schema pourra définir localement un helper
qui extrait `Schema.Schema.Type<typeof SchemaValue>`, sans que
`@craft-ts/i18n` importe Effect.

### Messages

La syntaxe d’écriture doit rester compacte :

```ts
const count = number('count', Count);
const amount = money('amount', Money);

const fr = defineLocaleLike(en, 'fr-FR', {
  cart: {
    total: msg`Le total est de ${amount}.`,
    items: plural(count, {
      one: msg`Vous avez ${count} article.`,
      other: msg`Vous avez ${count} articles.`,
    }),
  },
});
```

`msg` doit construire une représentation structurée du message et non
concaténer immédiatement des chaînes. Cette représentation permettra de
produire du runtime, des diagnostics, des assets JSON ou un format ICU.

### Pluriels

Les catégories doivent être déterminées par `Intl.PluralRules`/CLDR :

```text
zero, one, two, few, many, other
```

Le contrat d’une locale doit exiger les catégories pertinentes pour cette
locale, sans obliger le français à implémenter les catégories de l’arabe.

Le build doit refuser une catégorie manquante. Aucun fallback silencieux vers
`other` ne doit masquer une traduction incomplète lorsque le mode strict est
activé.

### Formatage

Créer des profils de formatage explicites :

```text
money
number
integer
percent
compact-number
date-short
date-long
date-time
relative-time
```

Chaque profil contrôle notamment :

- locale ;
- devise ;
- précision ;
- nombre maximal de décimales ;
- arrondi ;
- notation compacte ;
- fuseau horaire pour les dates.

Une limite d’affichage ne doit jamais tronquer silencieusement une valeur
financière. Si une notation compacte est souhaitée, elle doit être un profil
explicite et testable.

## Sources des traductions et assets

### Source recommandée

La source de vérité est un catalogue TypeScript typé, afin que les erreurs
soient visibles dans l’éditeur et par `tsc`.

### Format de livraison

Le build pourra produire des assets JSON par locale :

```text
dist/assets/i18n/en-US.json
dist/assets/i18n/fr-FR.json
```

Les JSON sont des artefacts de livraison, pas la source de vérité. Le build
doit vérifier les clés, tokens, catégories de pluriels et identifiants de
formatters avant de les émettre.

Pour un token custom sérialisé, le JSON conserve un identifiant stable :

```json
{
  "token": "app.order-status",
  "name": "status"
}
```

Le formatter correspondant est enregistré dans l’application côté navigateur
et côté serveur.

## Intégration automatique dans `craft create`

Modifier le générateur de projet dans :

```text
libs/dev-tools/src/scripts/create/create-project.ts
```

### Dépendances installées

Pour les modes `plain` et `effect`, le starter doit installer :

```json
{
  "dependencies": {
    "@craft-ts/i18n": "<version Craft TS>"
  }
}
```

En mode `plain`, il ne doit pas installer :

```text
@craft-ts/i18n-effect
@craft-ts/effect pour l’i18n
effect pour l’i18n
```

En mode `effect`, le starter doit en plus installer et configurer
`@craft-ts/i18n-effect` et sa version compatible d’`effect`.

`@craft-ts/i18n-effect` fournit l’adapter entre les tokens i18n et Effect
Schema/Effect services. Il doit réutiliser `@craft-ts/i18n` plutôt que
reproduire son catalogue ou son runtime.

### Fichiers générés

Le starter doit créer automatiquement :

```text
src/i18n/catalog.ts
src/i18n/locales/en-US.ts
src/i18n/locales/fr-FR.ts        # si plusieurs locales sont demandées
src/i18n/project-tokens.ts
src/i18n/runtime.ts
src/i18n/typography.ts
src/i18n/index.ts
```

En mode `effect`, ajouter également :

```text
src/i18n/effect.ts
src/i18n/effect-layer.ts
```

Ces fichiers configurent les formatters et le loader via Effect, sans modifier
les messages ni les clés.

Le starter doit fournir au minimum un message avec :

- un montant ;
- une date ;
- un nombre ;
- un pluriel ;
- une traduction dont l’ordre varie entre deux locales.

### Options de création

Ajouter une configuration explicite, par exemple :

```text
--locales en-US,fr-FR
--default-locale en-US
--i18n strict
```

Si aucune locale n’est fournie, générer une configuration minimale valide avec
une seule locale et un fichier de configuration indiquant où en ajouter.

### Scripts générés

Ajouter :

```json
{
  "i18n:check": "craft i18n check",
  "i18n:test": "craft i18n test"
}
```

Les scripts doivent être intégrés à la CI générée et au workflow de qualité du
starter. Le build doit échouer si le catalogue n’est pas complet.

### Documentation et règles agent

Mettre à jour les fichiers générés :

```text
AGENTS.md
.agents/skills/craft-ts-project/SKILL.md
README.md
```

Documenter :

- où ajouter une clé ;
- comment ajouter une locale ;
- comment créer un token custom local ;
- comment ne pas importer Effect pour l’i18n ;
- comment lancer les tests de pages réelles.

## Tests à mettre en place

### Tests de types

Ajouter des fixtures positives et négatives dans le style de `libs/test-type` :

- clé inconnue refusée ;
- clé manquante refusée ;
- locale supplémentaire refusée ;
- paramètre manquant refusé ;
- paramètre de mauvais type refusé ;
- token `money` utilisé avec une date refusé ;
- catégorie de pluriel manquante refusée.

### Tests runtime

Avec Vitest :

- validation des catalogues ;
- résolution des tokens ;
- formatage par locale ;
- pluriels et fractions ;
- dates invalides ;
- nombres négatifs et extrêmes ;
- chargement et cache des locales ;
- absence de token non résolu.

### Tests des pages réelles

Ne pas faire reposer la garantie principale sur une page de stress artificielle.
Les tests Playwright doivent parcourir les routes réelles de l’application avec
des données déterministes :

```text
route × locale × scénario métier × viewport
```

Les scénarios doivent inclure :

- zéro, un et plusieurs éléments ;
- toutes les catégories de pluriel ;
- montants courts et très longs ;
- noms et titres longs ;
- dates longues ;
- textes RTL ;
- textes sans espaces ;
- locale pseudo-longue de test.

Les assertions doivent vérifier :

- texte visible ;
- absence de `scrollWidth` supérieur au viewport ;
- absence de clipping inattendu ;
- absence de chevauchement ;
- boutons et labels encore utilisables ;
- `lang` et `dir` corrects ;
- SSR et hydratation cohérents.

Les screenshots sont complémentaires et doivent cibler les pages critiques,
les viewports mobiles et les locales à risque.

### Tests typographiques

Le starter doit générer une typographie explicite :

- famille de fonte définie ;
- fallback documenté ;
- rôles `heading`, `body`, `label`, `button`, `caption` ;
- `font-size` et `line-height` définis pour chaque rôle ;
- tokens CSS centralisés ;
- support de la taille racine augmentée.

Les tests navigateur doivent attendre `document.fonts.ready`, puis vérifier sur
les pages réelles :

- fonte effectivement disponible ;
- taille calculée ;
- graisse ;
- interligne ;
- caractères couverts par la fonte ou fallback explicitement autorisé.

## Phasage

### Phase 1 — contrat et package indépendant

- créer `libs/i18n` ;
- définir les types de catalogue et tokens ;
- implémenter `msg`, `plural` et les formatters de base ;
- ajouter les tests de types et runtime ;
- vérifier l’absence de dépendance Effect.

### Phase 2 — tokens custom projet

- ajouter `defineToken` et `defineTokenFactory` ;
- documenter les wrappers locaux ;
- tester les tokens composites ;
- définir le format sérialisable des tokens custom.

### Phase 3 — locales, assets et validation build

- ajouter le registre de locales ;
- générer les JSON ;
- implémenter `craft i18n check` ;
- vérifier les paramètres, pluriels et formatters ;
- intégrer l’échec au build et à la CI.

### Phase 4 — création d’application

- modifier `craft create` ;
- générer les fichiers i18n ;
- installer `@craft-ts/i18n` dans tous les modes ;
- installer `@craft-ts/i18n-effect` uniquement en mode `effect` ;
- générer l’adapter et les providers Effect uniquement en mode `effect` ;
- générer la configuration typographique ;
- ajouter les scripts et fixtures de test ;
- mettre à jour les tests de `create-project`.

### Phase 5 — tests pages réelles et typographie

- ajouter le harness Playwright locale/scénario ;
- activer les viewports mobiles ;
- ajouter les assertions DOM de layout ;
- ajouter les tests de fonte et taille calculée ;
- ajouter les screenshots des pages critiques ;
- ajouter SSR/hydratation multilingue.

## Critères d’acceptation

- Une application créée en mode `plain` possède l’i18n fonctionnel sans Effect.
- Une application créée en mode `plain` n’installe aucun package Effect lié à
  l’i18n.
- Une application créée en mode `effect` installe et configure
  `@craft-ts/i18n-effect`.
- Une clé inconnue échoue au typecheck.
- Une locale incomplète échoue au typecheck ou à `i18n:check`.
- Un paramètre de mauvais type échoue au typecheck.
- Une catégorie de pluriel nécessaire ne peut pas être omise.
- Un token custom peut être défini dans l’application sans modifier la lib.
- Les pages réelles sont testées avec des locales et données limites.
- Les tests attendent le chargement des fontes avant les mesures.
- Une régression de taille, interligne, clipping ou overflow échoue en CI.
- Le package lié à Effect n’est ajouté que lorsque le mode `effect` est choisi.

## Hors périmètre initial

- interface d’administration des traductions ;
- synchronisation avec un TMS ou un CMS ;
- traduction automatique ;
- correction grammaticale automatique ;
- adaptation automatique de `font-size` selon la longueur d’une traduction ;
- package i18n dépendant d’Effect installé dans une application `plain`.
